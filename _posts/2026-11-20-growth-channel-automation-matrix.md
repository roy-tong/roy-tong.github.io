“帮我把这个产品发到所有平台”听起来像一项任务，实际里面混了四种工作：内容规划、素材生产、真实写入和结果复盘。

如果只检查文案有没有生成，就无法知道渠道动作是否真正完成；如果只检查发送回执，也无法知道内容是否被看到、有人回复或产生采用。

增长自动化应该先画渠道矩阵，把每个平台能承担的工作写到具体一层。下面用我开发的 Growovo 做示例：它是一套增长执行工具，我把渠道规则、授权、执行记录和复盘放在同一条流程里检查。

## 一、先把渠道任务拆成五层

| 层 | 要回答的问题 | 合格证据 |
|---|---|---|
| 研究 | 目标用户和相关讨论在哪里？ | 来源链接、检索范围、候选对象 |
| 内容 | 是否产生符合渠道要求的素材？ | 审稿记录、候选稿、作业单 |
| 授权 | 谁允许哪个账号执行什么动作？ | 授权范围、配额、有效期 |
| 执行 | 是否真实发布、回复或发送？ | 平台回执、页面回读、异常记录 |
| 结果 | 是否产生互动、使用或转化？ | 平台读数、网站事件、业务记录 |

这五层不能互相替代。研究完成不代表内容完成，内容完成不代表已发布，发布成功也不代表增长成立。

## 二、按真实能力分配自动化

按 Growovo 截至 2026-11-20 的公开能力口径，可以先这样理解：

| 渠道 | 当前可组织的工作 | 自动化边界 |
|---|---|---|
| Email | 发送、队列、记录、跟进 | 有自动发送路径，仍需授权与实际环境验证 |
| X | 发布、回复、搜索、运营数据 | 常驻非 API 自主发布受限；特定单次动作需人工明确授权 |
| GitHub | 仓库体检、Issue／PR 巡检、搜索、回复候选 | 读取已验证，写入需人工首跑验证 |
| Reddit／Hacker News | 社区发现、讨论参与、发布候选 | 读写验证程度不一，不能承诺无人值守 |
| LinkedIn | 潜客研究、连接与消息候选 | 写入尚未完成真实账号验证 |
| 小红书／公众号／知乎／抖音 | 内容规划、规范检查、人工运营任务 | 主要辅助内容运营，无完整自动发布承诺 |

这张表描述的是产品能力边界，不是一次真实账号验收结果。实际执行前仍需核对版本、账号权限和平台规则。

## 三、给每个渠道写一张作业单

不要只写“本周运营 X 和小红书”。把任务写成可以验收的形式：

| 字段 | 示例 |
|---|---|
| 目标 | 获得目标开发者的有效回复 |
| 对象 | 正在讨论本地 AI 部署的开发者 |
| 动作 | 回复候选 5 条，人工确认后执行 |
| 系统交付 | 研究记录、候选回复、授权队列 |
| 人工动作 | 审核对象与措辞，处理未知回执 |
| 停止条件 | 账号异常、对象不适配、配额用完 |
| 结果证据 | 实际可见回复、有效对话、后续采用记录 |

小红书等以人工运营为主的渠道，系统交付可以是选题、封面文案、正文和发布检查单。不要把“稿件进入队列”写成“平台发布完成”。

## 四、自动执行要保留三个出口

**人工首跑**：新账号、新写入路径和新平台先由人完成一次，确认权限、字段、可见性和异常表现。

**异常停止**：遇到限制、未知状态或页面无法回读，不自动重发，不换账号绕过。

**结果复核**：把执行记录与互动、采用分开，避免用发送量证明增长。

这些出口不是自动化不足的装饰，而是对外动作必须具备的责任边界。

## 五、Growovo 当前适合交付什么

它可以把增长目标、渠道研究、内容供给、部分授权执行、运营记录和复盘组织在同一条流程里。对没有专职增长人员的小团队，价值在于减少任务散落和结果断档。

但它还不能接管所有营销渠道，也不能保证用户增长。产品吸引力、内容质量、平台分发和真实需求都在结果里起作用。

最值得先验证的不是“支持多少平台”，而是一个具体渠道任务能否反复跑通：人工工作量是否下降，质量是否保持，结果能否被独立复核。
