    <h1>Verovo：供应商出口不是买家的证据</h1>
    <p class="post-subtitle">控制域、程序来源检查、结果观察者等级、规范完成轴和仅证据交接。</p>
    <div class="post-meta">

      <span>7分钟阅读</span>

  <div class="prose">
    <p>两个CSV文件可能包含相同的行，但仍然无法调和任何有意义的内容。 如果同一供应商生成了两个导出，文件将在一个控制域内建立一致性。 他们没有建立买方的独立确认。</p>

<p>这是控制域问题，它位于人工智能计费、交付验收和任务经济学之下。 买方验证者需要知道的不仅仅是是否<code class="language-plaintext highlighter-rouge">amount_a == amount_b</code>。 它需要知道谁控制了每个来源，谁收集了它，它是如何被确认的，以及声称的接受身份是否具有任何权威。</p>

<p>Verovo明确了这些关系。 它的买家证据检查是程序性元数据检查，而不是加密身份证明。 这是一个更狭隘、更有用的主张：不一致的来源可以被决定性地拒绝，而不是通过合理的文件名或<code class="language-plaintext highlighter-rouge">verified=true</code>领域。</p>

<h2 id="buyer-provenance-is-a-conjunction-not-a-label">买家来源是连接词，而不是标签</h2>

<p>出处词汇包含八个规范化字段：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>source_party
source_affiliation
control_domain
collector_party
collection_method
independence
confirmation_process
source_path
</code></pre></div></div>

<p><code class="language-plaintext highlighter-rouge">source_association</code>和<code class="language-plaintext highlighter-rouge">collected_by</code>被接受为隶属关系和收藏家的别名，然后投射到规范名称中。 缺失的价值变成了<code class="language-plaintext highlighter-rouge">unknown</code>.</p>

<p>当前的买方证据审查要求以下所有内容：</p>

<ul>
  <li><code class="language-plaintext highlighter-rouge">source_party</code>, <code class="language-plaintext highlighter-rouge">source_affiliation</code>, <code class="language-plaintext highlighter-rouge">control_domain</code>，还有<code class="language-plaintext highlighter-rouge">collector_party</code>确切地说<code class="language-plaintext highlighter-rouge">buyer</code>;</li>
  <li><code class="language-plaintext highlighter-rouge">independence=buyer_independent</code>;</li>
  <li>一个非空的<code class="language-plaintext highlighter-rouge">source_ref</code>存在；</li>
  <li>收藏不是<code class="language-plaintext highlighter-rouge">ocr</code>, <code class="language-plaintext highlighter-rouge">invoice2data</code>, <code class="language-plaintext highlighter-rouge">self_declared</code>, <code class="language-plaintext highlighter-rouge">self_attested</code>，或者未知；</li>
  <li>确认不是自我声明的、自我证明的或未知的；</li>
  <li>任何源、路径、集合、确认、隶属关系、域或收集器字段都没有带有明确的供应商控制标记。</li>
</ul>

<p>以简化的形式：</p>

<div class="language-python highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="n">qualified</span> <span class="o">=</span> <span class="p">(</span>
    <span class="nb">all</span><span class="p">(</span><span class="n">field</span> <span class="o">==</span> <span class="s">"buyer"</span> <span class="k">for</span> <span class="n">field</span> <span class="ow">in</span> <span class="n">PARTY_FIELDS</span><span class="p">)</span>
    <span class="ow">and</span> <span class="n">independence</span> <span class="o">==</span> <span class="s">"buyer_independent"</span>
    <span class="ow">and</span> <span class="n">source_ref</span>
    <span class="ow">and</span> <span class="n">collection_method</span> <span class="ow">not</span> <span class="ow">in</span> <span class="n">UNQUALIFIED_METHODS</span>
    <span class="ow">and</span> <span class="n">confirmation_process</span> <span class="ow">not</span> <span class="ow">in</span> <span class="n">UNQUALIFIED_CONFIRMATION</span>
    <span class="ow">and</span> <span class="ow">not</span> <span class="n">any_vendor_control_markers</span>
<span class="p">)</span>
</code></pre></div></div>

<p>A<code class="language-plaintext highlighter-rouge">buyer</code>包含显式供应商标记的清单路径下的行未能关闭。 供应商路径不能重新标记为买家独立性。 两个供应商控制的出口可能支持<code class="language-plaintext highlighter-rouge">Vendor Reconciled</code>；他们无法支持<code class="language-plaintext highlighter-rouge">Buyer Verified</code>.</p>

<p>输出也区分了<code class="language-plaintext highlighter-rouge">independence_assertion</code>来自<code class="language-plaintext highlighter-rouge">independence_basis</code>。 干净的结果只是<code class="language-plaintext highlighter-rouge">procedural_metadata_only</code>。 这不是身份密码学，实现是这样说的，而不是将元数据视为签名。</p>

<h2 id="outcome-class-and-observer-grade-are-separate-axes">结果班和观察者等级是分开的轴</h2>

<p>结果验证存在与来源独立性相同的胁迫问题。 “已解决”不是一个同质的单位。</p>

<p>一个公共合成夹具模拟了每项解决的争议，有十条记录：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>outcome_class:
  resolved            4
  assumed_resolved    3
  escalated           2
  abandoned           1

observer_grade:
  affected_party      5
  self_attested       5
</code></pre></div></div>

<p>我把夹具复制到临时目录中，并运行其已发货的复制品。 实际产出是：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>Provider headline: resolved + assumed_resolved
  7/10 = 70%

Audited: resolved + affected_party attested only
  4/10 = 40%

Gap: 30 percentage points
UNPROVABLE: 10/10 records carry no incrementality evidence
REPRODUCED
</code></pre></div></div>

<p>四个经过审计的记录要求两者<code class="language-plaintext highlighter-rouge">outcome_class=resolved</code>和<code class="language-plaintext highlighter-rouge">observer_grade=affected_party</code>。 三个假定的分辨率没有进入该分母。 无论观察者等级如何，升级都不会成为解决方案。</p>

<p>最后一行同样重要：十条记录中没有一条包含增量证据，因此夹具无法证明人工智能导致了分辨率。 这并不能使计数为零。 它将索赔限制在指定结果和观察者定义上。</p>

<p>这个<a href="https://github.com/roy-tong/Verovo/blob/main/conformance/evidence/assumed-resolution/run_case.py">案例跑者</a>计算两个费率，并通过发货代码生成结算披露。 它模拟了争议形式；它不是对讲机客户数据或对供应商的指控。</p>

<h2 id="period-intake-is-a-join-with-explicit-loss-reporting">期间摄入量是与明确损失报告的结合</h2>

<p>规范期结合了五种输入：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>tasks.csv      task identity and type
runs.jsonl     execution identity and task linkage
usage.jsonl    technical usage and optional financial amount
bills.csv      supplier charge representation
outcomes.csv   delivery and business outcome evidence
</code></pre></div></div>

<p>进气层保留间隙，而不是将它们隐藏在总数中：</p>

<table>
  <thead>
    <tr>
      <th>输入条件</th>
      <th>摄入行为</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>重复的<code class="language-plaintext highlighter-rouge">run_id</code>或者<code class="language-plaintext highlighter-rouge">usage_id</code></td>
      <td>稍后的行被忽略并重复打开</td>
    </tr>
    <tr>
      <td>重复的<code class="language-plaintext highlighter-rouge">charge_id</code></td>
      <td>保留了第一次预订的代表，重复报告，完整性受损</td>
    </tr>
    <tr>
      <td>不含货币的费用</td>
      <td><code class="language-plaintext highlighter-rouge">financial_status=unknown</code>；不假定案例货币</td>
    </tr>
    <tr>
      <td>无需成本的金融化使用</td>
      <td><code class="language-plaintext highlighter-rouge">unpriced</code>加<code class="language-plaintext highlighter-rouge">missing_amount</code>，从不为零</td>
    </tr>
    <tr>
      <td>没有数量的定价规则</td>
      <td><code class="language-plaintext highlighter-rouge">missing_quantity</code>，从不为零</td>
    </tr>
    <tr>
      <td>货币与案例不同</td>
      <td>排除和命名的行；规范运行拒绝混合货币案例</td>
    </tr>
    <tr>
      <td>没有任务链接的账单或使用</td>
      <td>成本仍然未分配，而不是平均分配</td>
    </tr>
    <tr>
      <td>与多个任务候选者关联的共享运行</td>
      <td>没有一个任务是默默选择的</td>
    </tr>
  </tbody>
</table>

<p>一个供应商、一个帐户和一个货币是硬规范范围限制。 匹配账单不能绕过单供应商检查。 已批准的定价规则可以重新计算费用，但规则重新定价和跨来源对账仍然是不同的轴心。</p>

<p>实现还对任务、运行和结果覆盖集进行一次索引，而不是重新扫描每个任务的每个源行。 发布说明中的4000行合成基准从大约0.66秒下降到0.071秒，覆盖率相同。 这种优化是有用的，因为它没有改变证据语义。</p>

<h2 id="completion-has-four-axes-and-fail-can-be-complete">完成有四个轴，失败可以完成</h2>

<p>规范金融不会返回一个通用健康分数。 它返回四个完成状态：</p>

<ul>
  <li><code class="language-plaintext highlighter-rouge">finance_status</code>：财务记录、对账差距和成本分配是否已关闭？</li>
  <li><code class="language-plaintext highlighter-rouge">verification_status</code>：适用的结果是否具有决定性的买方程序验证？</li>
  <li><code class="language-plaintext highlighter-rouge">delivery_status</code>：每项任务都有决定性的交付接受通过或失败的证据吗？</li>
  <li><code class="language-plaintext highlighter-rouge">economics_status</code>：适用的结果经济学，包括成本和成功/价值证据，是否完整？</li>
</ul>

<p>遗漏的结果来源使验证、交付和经济<code class="language-plaintext highlighter-rouge">not_applicable</code>；它不会使一个仅金融的时期变得部分。 当前但空洞的结果来源无法掩盖经济差距。</p>

<p>果断的交付<code class="language-plaintext highlighter-rouge">FAIL</code>是完整的证据。 买方有足够的信息拒绝交货；不确定性不等同于负面结果。 此规则阻止报告层仅将有利结果视为已完成的工作。</p>

<p>投资回报率也与每次验证成功的成本是分开的。 缺少验证值可能会使ROI为空，而成本和验证成功成本仍然可以计算。 未经验证的供应商结果是未知的，不是成功也不是失败。</p>

<h2 id="acceptance-identity-comes-from-a-controlled-organization">接受身份来自受控组织</h2>

<p>交货验收需要超过一个<code class="language-plaintext highlighter-rouge">accepted_by</code>字符串。 清单必须声明一个受控的买方组织<code class="language-plaintext highlighter-rouge">org_id</code>和一个非空的<code class="language-plaintext highlighter-rouge">acceptance_signers</code>列表。</p>

<p>对于每行验收，规范财务检查：</p>

<ol>
  <li>受控组织存在；</li>
  <li>签署人不是供应商；</li>
  <li>签署人属于授权签署人名单；</li>
  <li>任何声明的<code class="language-plaintext highlighter-rouge">accepted_by_org</code>匹配该组织的ID或名称。</li>
</ol>

<p>伪造的买家标签、未知组织、供应商自我接受或缺少授权<code class="language-plaintext highlighter-rouge">UNPROVABLE</code>。 买家验证的成功也需要<code class="language-plaintext highlighter-rouge">accepted_by</code>和<code class="language-plaintext highlighter-rouge">accepted_at</code>；缺少时间戳产生<code class="language-plaintext highlighter-rouge">UNKNOWN</code>.</p>

<p>还有一个额外的交叉检查：如果任务有不合格的接受行，收费级别的买家已验证<code class="language-plaintext highlighter-rouge">PASS</code>因为那个任务被降级为<code class="language-plaintext highlighter-rouge">UNPROVABLE</code>。 干净的算术结果不能弥补对同一任务的未经授权的接受。</p>

<p>这是程序权威，而不是自我描述。 清单的受控组织是实现所认可的凭据边界。</p>

<h2 id="a-hash-proves-handoff-integrity-not-external-truth">哈希证明了交接的完整性，而不是外部真相</h2>

<p>Growovo可以将执行和结果记录交给Verovo。 进口商验证移交模式，在主体上重新计算SHA-256，不包括<code class="language-plaintext highlighter-rouge">integrity_sha256</code>和<code class="language-plaintext highlighter-rouge">generated_at</code>，递归地拒绝类似凭据的字段，并要求：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>booking_status = evidence_only_not_canonical
external_action_executed_by_export = false
</code></pre></div></div>

<p>然后，导入的证据记录指出：</p>

<div class="language-text highlighter-rouge"><div class="highlight"><pre class="highlight"><code>source_integrity_verified = true
integrity_meaning = unchanged_json_body_not_external_truth
receipt_verified_by_verovo = false
business_outcome_observed_by_verovo = false
payment_authorization = false
terminal_state = DELIVERED_WITH_GAP
premises_do_not_upgrade_grade = true
</code></pre></div></div>

<p>这是一个精确的完整性边界。 哈希显示，自Growovo计算以来，JSON主体没有改变。 这并不能证明发生了外部行动、供应商接受交货或存在收入。 预订需要单独的来源映射和审查。</p>

<p>同样的区别出现在提供商清单录取中。 本地文档可以声明引擎身份、处理可执行哈希、资源限制、就绪性检查、覆盖范围、清理和原始快照摘要。 必需的失败或未知的检查拒绝录取；可选的检查会降低它；未发布的清理拒绝它。 结果仍然有<code class="language-plaintext highlighter-rouge">live_engine_contacted=false</code>。 形成良好的适配器合同不是实时集成测试。</p>

<h2 id="reuse-means-preserving-definitions-across-periods">重复使用意味着跨时期保留定义</h2>

<p>第二个会计期应该重复使用来源要求、来源映射、结果类、观察者等级和完成语义。 它不应该自动重复使用上一时期的接受或独立性声明。</p>

<p>因此，有用的比较不仅仅是金额deltas：</p>

<ul>
  <li>哪些来源更改了控制域或收集器；</li>
  <li>哪些链接缺失或模棱两可；</li>
  <li>哪个结果分母改变了定义；</li>
  <li>接受签署人失去或获得授权；</li>
  <li>哪个完成轴改变了；</li>
  <li>解决新的差距需要多少人力工作。</li>
</ul>

<p>我为这篇文章运行了任务经济学、期间摄入量、覆盖范围和规范财务套件：通过了54项测试。 它们涵盖了重复身份、跨货币和跨帐户范围、缺失金额、供应商控制的重新标签、伪造买家字符串、供应商自我接受、空结果、决定性交付失败、未定价使用和未分配的共享成本。</p>

<p>实施的核心约束是保守的，但具有可能性：来自不同方的证据可以回答不同的问题，缺失的答案可以保持可见，而不会阻止每个计算。 买家可以核对一项指控，让交货未解决，并且仍然确切地知道接下来必须收到哪些证据。</p>
