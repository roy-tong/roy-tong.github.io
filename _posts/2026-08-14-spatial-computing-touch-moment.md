触控屏普及之前，移动设备已经能够显示网页、运行应用、播放视频，也可以用按键和手写笔完成操作。但真正改变计算习惯的，不只是屏幕变小或性能变强，而是点击、滑动、拖拽、双指缩放这些动作形成了一套共同语言。

用户不必为每一个应用重新学习怎样选中、怎样移动、怎样返回。开发者也不必从零定义一套输入设备。稳定的交互原语，把硬件能力变成了可以重复利用的平台能力。

今天的空间计算已经能够识别环境、追踪手眼、放置三维内容，也能把多个窗口固定在真实空间里。很多 Demo 第一次看令人惊叹，日常使用却仍然容易退回二维窗口、传统菜单和短时体验。

问题未必是空间内容不够多，而是空间还没有形成自己的“触控时刻”。

这里的“触控时刻”不是等待某一个神奇手势。它指的是一组跨设备、跨应用相对稳定的动作，以及围绕这些动作形成的系统契约：用户知道自己正在看什么、选中了什么、系统将做什么、失败后怎样恢复；开发者知道注意、选择、操作和意图分别应该由哪种输入承担。

只有到了这一步，空间内容才可能从一次性演示变成计算平台。

## 一、不能把鼠标和触控屏直接搬进空间

鼠标和触控之所以高效，依赖几个常被忽略的条件：操作面是稳定的，目标通常处在同一平面，手可以得到桌面或屏幕支撑，点击有明确边界，界面也能持续占据视觉中心。

空间交互没有这些默认条件。

- 目标有远近、遮挡和朝向，视线落点与手部落点都可能漂移；
- 手臂悬空会累，细小抖动会被放大，长时间凝视也会产生负担；
- 用户会走动、转身，与真实的人和物共享注意力；
- 语音会受到公共场合、噪声、隐私和语言表达能力的限制；
- 一个动作可能改变真实环境中的设备状态，错误不再只是关掉一个窗口。

因此，空间计算不是在三维场景里画更多按钮，也不是用手指模拟一只悬空鼠标。它需要重新分配输入职责：什么用于表达注意，什么用于确认选择，什么适合连续操控，什么适合描述开放目标。

Apple 在 visionOS 的设计指南中把眼睛、手和语音都视为自然输入，并强调内容应放在舒适范围内，避免用户为了操作反复大幅移动头颈。Microsoft 的混合现实指南则把 gaze 与 commit 分开：注视可以指向目标，但确认需要手势、语音、按钮或停留等另一种机制。

两者背后的共同原则很重要：**看见，不等于同意；注意，不等于执行。**

## 二、空间 Demo 很强，日常习惯却很弱

许多空间体验的问题，不是单次任务做不到，而是每个应用都在发明自己的动作。

同样是注视，在一个应用里用于高亮，在另一个应用里触发选择；同样是捏合，有时代表点击，有时代表抓取，有时又进入缩放。用户还要猜测手是否被识别、对象是否可以操作、动作已经生效还是系统仍在等待。

这种不一致会产生四层成本：

1. **发现成本**：用户不知道哪些对象可以操作；
2. **学习成本**：进入新应用就要重新记忆动作；
3. **确认成本**：系统反馈不清楚，用户不敢继续；
4. **恢复成本**：误触之后找不到撤销、退出或接管方式。

空间交互也常把多模态理解成相互替代：既可以手势，也可以语音，也可以控制器。但真正有价值的多模态不是提供三套入口，而是让不同模态各自承担最擅长的语义，并能组合成一句完整的“操作语言”。

语音擅长表达开放目标，却不擅长在密集物体中精确指代“右边第三个小零件”；凝视和指向擅长提供上下文，却不应该单独承担高风险确认；手势适合承诺、抓取和连续调整，却不适合描述复杂约束。

空间计算的交互突破，可能首先发生在这些能力之间的分工，而不是某一种能力的准确率再提高几个百分点。

## 三、先形成四个稳定原语

一套可用的空间语言，至少需要把“看、指、捏、说”分成四种不同职责。

| 原语 | 主要语义 | 适合做什么 | 不应该默认做什么 |
| --- | --- | --- | --- |
| 看 | 注意与上下文 | 高亮候选、读取状态、缩小搜索范围 | 自动确认或执行 |
| 指 | 对象与方向 | 消除“这个、那里”的歧义，粗选区域 | 高精度连续操作 |
| 捏 | 承诺与操控 | 确认、抓取、拖动、缩放、细调 | 表达复杂目标 |
| 说 | 目标与关系 | 描述任务、属性、约束和结果 | 独自承担精确空间定位 |

“看”让系统知道用户当前关注的上下文；“指”把开放空间压缩到一个对象或区域；“捏”把关注变成明确承诺，并提供连续控制；“说”则把动作从“移动它”提升到“把它放在不挡住门、又能被两个人看到的位置”。

这四个词不是最终标准，也不要求每台设备拥有相同传感器。关键是建立稳定语义。OpenXR 的 action 机制采用相似思路：应用先声明有业务含义的动作，再由运行时把不同硬件的按键、姿态或输入方式绑定到这些动作。平台稳定的不是某一枚实体按钮，而是“选择”“抓取”“移动”这样的意图。

一组交互原语要成为平台语言，还必须同时具备六个属性：

- **可发现**：用户能看出对象是否可操作；
- **一致**：同一动作在不同应用里保持核心含义；
- **有状态**：悬停、选中、执行、完成与失败都有可见反馈；
- **可宽恕**：误操作可以取消、撤销或回滚；
- **可适配**：允许手、眼、语音、控制器或辅助设备做等价映射；
- **可组合**：简单动作可以组成复杂任务，而不是每次重学新手势。

触控屏成功并不是因为“点击”足够酷，而是这些条件一起成立。空间计算也一样。

## 四、从 Point and Click 走向 Point and Ask

桌面计算的代表性动作是 Point and Click：先定位，再执行一个确定命令。空间计算在保留 Point and Act 的同时，会增加另一种重要组合：Point and Ask。

用户看向设备、指向零件，然后问：“这个为什么一直闪？”

这一组动作同时提供了对象、场景、问题和用户意图。系统不必要求用户先知道设备名称、型号、零件编号和菜单路径，也不需要纯视觉模型在整个画面中猜测“这个”指什么。

但 Point and Ask 不是把语音助手放进头显。要变成可靠交互，系统至少需要显式呈现四件事：

1. 它识别的是哪个对象或区域；
2. 它怎样理解用户的目标；
3. 接下来只是回答、生成预览，还是会执行动作；
4. 用户怎样修正指代、取消执行或回到上一步。

例如，“把这面墙换成深灰色”可以先产生局部预览；“关闭这个阀门”则必须显示对象、影响范围和确认状态；“拆下这一块”应该把步骤叠加在对应结构上，并允许用户随时暂停。

空间交互的优势不是取消界面，而是把界面从固定页面变成围绕对象、任务和风险即时出现的控制层。

## 五、直接操作与 Agent 要形成快慢双循环

空间计算加入 Agent 后，最容易出现的误区是把所有操作都交给自然语言。这样看似智能，实际会牺牲速度、确定性和控制感。

低风险、即时、可逆的动作，仍然适合直接操作：移动窗口、旋转模型、调整大小、切换显示层。用户做出动作，系统立即响应，形成毫秒到秒级的快循环。

需要理解目标、规划步骤、调用工具或等待外部结果的任务，才适合进入 Agent 慢循环：检查一套设备、比较多个方案、生成布置建议、协调不同系统完成任务。

慢循环不能是黑箱。用户需要持续看到：

- Agent 正在作用于哪些对象；
- 已经完成哪一步，下一步是什么；
- 哪些判断来自已知事实，哪些仍是推测；
- 哪一步需要确认，何时可以暂停或接管；
- 失败后真实世界和数字状态分别停在哪里。

可以把两种循环理解为一组分工：**直接操作负责局部确定性，Agent 负责跨步骤协调；用户始终保留意图、风险和最终承诺。**

这也解释了为什么凝视不应直接执行。人的目光持续移动，如果每次看见都触发动作，注意力就会被误解成授权。Microsoft 的眼动交互指南明确提醒，眼动追踪始终处于开启状态，因此不应让每一次注视都立即触发行为。空间 Agent 尤其需要把“系统知道我在看什么”和“我允许系统改变什么”隔开。

## 六、真正的平台不是 App 阵列，而是 World Canvas

今天很多空间设备仍然以 App 为中心：用户打开应用，把一个窗口或模型摆在房间里，再切换到另一个应用。空间只是桌面的延伸，应用仍然拥有彼此割裂的对象和状态。

如果空间计算要成为新的计算平台，组织单位可能会从 App 逐渐转向 World Canvas：一个由真实物体、数字对象、人物、位置、关系、状态和权限共同构成的任务环境。

在这个环境中，一把椅子不只是图像识别结果。它有身份、位置、尺寸、所属人、可移动性、历史状态，也可能与“会议布置”“家庭安全”“室内设计”等任务相关。一个数字模型也不只属于创建它的应用，而可以在获得授权后被其他工具和 Agent 引用。

这会产生一种比菜单命令更高层的输入：**Spatial Intent，空间意图。**

用户不再逐一指定应用与步骤，而是表达期望的世界状态：

- “让这块区域能够坐下六个人，同时保留通道”；
- “把所有可能碰到孩子的边角标出来”；
- “按照刚才的拆解顺序，告诉我下一步操作哪个部件”。

系统需要把意图翻译成对象关系、约束、候选方案和可执行步骤，再通过看、指、捏、说完成澄清与确认。

这不是取消 App，而是让 App 从信息容器转为能力提供者。工具仍然存在，但用户首先操作的是世界中的对象和任务。

## 七、用五级成熟度判断是不是空间计算

团队很容易把“内容放进三维空间”当成空间计算。更有区分度的判断方式，是看用户和空间对象之间形成了多深的关系。

| 等级 | 能力 | 用户得到什么 |
| --- | --- | --- |
| L0 显示 | 在空间中呈现窗口、图像或模型 | 看见内容 |
| L1 可选 | 能稳定识别、指向和选中对象 | 知道“这是哪个” |
| L2 可操作 | 能移动、修改、组合对象并获得反馈 | 改变局部状态 |
| L3 可完成 | 系统理解任务，协调多步操作并允许接管 | 得到完整结果 |
| L4 可持续协作 | 对象、关系、权限和任务状态跨时间、场景与工具延续 | 与人和 Agent 共同维护世界状态 |

L0 到 L2 主要解决内容和直接交互；L3 开始进入 Agent；L4 才真正触及平台层。等级越高，所需能力越不只是识别精度，还包括身份、权限、状态同步、错误恢复和跨工具协议。

这套分级也能避免一个常见错觉：一个视觉效果震撼的 L0 Demo，未必比一个画面朴素但能稳定完成任务的 L3 系统更接近平台。

## 八、用 30 到 60 秒测试原语，而不是展示世界观

早期空间产品不需要先拍一条宏大的未来生活视频。更有效的验证，是设计几个任何人都能在一分钟内理解成败的任务。

**遮挡测试**：让用户面对一个被部分遮挡的对象，通过侧身、注视和指向选中目标。观察系统能否保持对象身份，用户能否清楚知道当前选中了什么。

**识别—拆解—追问测试**：用户指向一个陌生装置，询问其作用，再要求显示拆解顺序。观察指代能否延续、步骤是否锚定正确部件、用户能否中断与纠错。

**改变规则测试**：用户暂停当前场景，提出“保留通道、减少一个座位”的新约束。系统先给出空间预览，用户确认后执行，并能一键回滚。观察意图、约束、预览和恢复是否形成闭环。

这三个测试分别检验选择稳定性、对象上下文和任务控制。它们比“支持多少手势”更接近真实平台能力。

## 结语：触控时刻是一套共同语法

空间计算的下一步，不只是更轻的设备、更大的视场角或更多三维内容。这些都重要，但它们不会自动生成新的计算习惯。

真正的转折点，会出现在用户不再思考“这个应用该怎么操作”，而能自然地看向对象、指出范围、确认动作、表达目标；系统则稳定地区分注意、选择、操控和授权，并让每一步都可见、可纠正、可恢复。

那时，“看、指、捏、说”才不再是四种炫技输入，而会成为像点击、拖拽、缩放一样的共同语法。直接操作与 Agent 也不再相互替代，而是在同一个空间任务中形成快慢双循环。

空间计算的“触控时刻”，最终不是一个手势被发明出来，而是人、对象、Agent 和真实世界之间，第一次拥有了一套稳定的协作协议。
